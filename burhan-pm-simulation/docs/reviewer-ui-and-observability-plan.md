# Reviewer UI Design

This document describes the reviewer UI goals and current implementation.

## Purpose

The reviewer must be able to understand:

- What the PM was asked to do
- What happened over time
- What each actor knew and did
- Why the run ended
- Whether the PM actually improved the situation

## Current Implementation

### Run List (Home)

- Create runs from any of the 4 scenarios
- See status, current sim time, scenario name
- Start, pause, resume controls

### Run Detail

- Mission title and visible brief
- Actor roster with names and roles
- Activity stream (reverse chronological)
  - Actor name + role per entry
  - "X ago" timestamps relative to current sim time
  - Merged world events + actor reasoning traces
- Speed control: 1x, 10x, 100x
- Post-run analysis (summary + judgment) when available
- Collapsible sections preserve open/closed state across auto-refresh

### Actor Detail

- Name, role, team
- Local time and working-hours status
- Recent observations
- Current commitments
- Inbox surfaces
- Visible work
- Reasoning traces

### Post-Run Analysis

After a run completes:

- **Story summary** — narrative of what happened
- **Qualitative judgment** — LLM evaluation of PM performance

Generated by Claude Sonnet 4.6 in a background thread.

## Design Principles

- Logs should read like workplace history, not event-type dumps
- Actor-facing and admin-only truth are clearly separated
- Internal runtime mechanics are hidden by default
- One primary question per screen
- Time and status emphasized consistently
- No raw JSON on primary surfaces unless toggled

## Admin Surfaces

Admin-only (via `/api/admin/` routes):

- Hidden truth (rubric, hidden success/failure conditions)
- Trigger inspector
- Raw event data
